# AIネイティブ 5/5（Web Standards Headless Design System Kit）ロードマップ（承認済み）

## Summary（結論）
この repo（web-components-factory）は、`custom-elements.json`（CEM）を単一の真実として DX/検証/AIツールを駆動する方針を既に採用している。
現状（`monoharada/cem-ci-mcp` 起点）は CEM生成+CIゲート / CEM駆動の fast validator / prefix変換 / DS-MCP（tools）/ docs 導線まで揃っており、AIネイティブの土台は強い。

一方で 5/5 に上げるためには、以下が不足している:
- CEMノイズの除去（例: bogus event の継承汚染）と回帰固定
- CEMの意味情報（enum/型/deprecation/cssProperties）強化（AIが値を外さない）
- 検証の二段構え（fast + strict）と診断スキーマの固定（機械可読）
- DS-MCP を “MCPの三本柱”（Tools/Resources/Prompts+Completion）へ拡張し、修正提案→再検証まで回す
- runtime loop（viewer smoke + console error）をAI/CIから呼べる形にする
- warning/deprecation の運用ガード（増殖防止、変更点の可視化）

この計画は 0〜6 のフェーズ/PR分割で段階導入し、前工程ほど “他工程すべての精度に効くもの” を先に行う。

## Current state audit（現状監査）
### 既に導入済み
- CEM生成（`npm run cem:analyze`）+ `custom-elements.json` のコミット運用
- CIゲート（CEM生成→ `git diff --exit-code custom-elements.json`）
- CEM駆動のマークアップ検証（内製 validator: 正規表現ベース、`viewer.html` + `src/demos.ts`）
- prefix変換（canonical = `dads-*`、tagNameのみ安全に置換する `cem:prefix`）
- Design System MCP（stdio）: `list_components` / `get_component_api` / `generate_usage_snippet` / `validate_markup`
- docs（CEM / validate / DS-MCP / Chrome DevTools MCP）

### 監査で見えた不足（根拠）
- CEMのスタイルAPI情報が不足:
  - `cssProperties=0`（`@cssprop/@cssproperty` が未整備）
  - deprecated 情報が機械可読ではない（CEMに未反映）
- CEMの意味情報が不足:
  - enum相当の属性が多いが、`type.text` は `string` のままになりやすい（許容値は description に埋まりがち）
- CEMノイズ:
  - analyzer の event 推論が `emitEvent(type, ...)` の `type` 引数をイベント名として誤認し、`name: "type"` のイベントを生成→継承で汚染が拡散しうる
  - base class が “custom element 扱い” になることがある（tagNameを持たないのに customElement=true など）
- 検証の二段構えが未整備:
  - fast path（正規表現）のみで、HTML AST の strict path が無い
  - warning 増殖を防ぐ仕組み（baseline/増分fail）が未整備
- DS-MCP が tools-only:
  - Resources / Prompts / Completion / structured output / 修正提案（patch + 再検証）が未整備
- runtime loop が “AIが呼べる形” ではない:
  - Playwright 等はあるが、viewer起点の最小 smoke を non-blocking で並走→安定後に blocking 化する運用が未整備

## Target definition: AI-native 5/5 DoD（チェックリスト）

検証（3）

- [ ] fast path はCI blocking で運用でき、strict は段階導入できる（最初 non-blocking）

修正（4）
- [ ] `suggest_fixes({ html, prefix? })` が patch/unified diff + 再検証結果を返す
- [ ] deprecated pattern（例: placeholder）を検知し、移行先を提示できる

運用（5）
- [ ] warning が増殖しない（baseline固定 + 増分fail）
- [ ] deprecation が機械可読で、AI/CI/Editor が同じルールで検知できる
- [ ] 半年後も壊れにくい（決定性・回帰・変更点可視化・Runbook）

### Phase 2: CEMの意味情報を高める（PR2）

- [ ] `cssProperties` が 0 から増える（主要コンポで一定数）
- [ ] deprecation が機械的に検知できる

## Decision points（分岐条件）
- Phase2（enum/型）: JSDoc union で `type.text` が改善するかを代表例で検証し、改善しない場合は postprocess/type抽出強化へ分岐
- Phase3（strict）: wctools が復旧しても差し替え可能なように diagnostics schema を先に固定
- tokens: cssProperties（公開 CSS vars）は CEM を優先、トークン体系は `ds://tokens` resource に分離可能（SoT を docs で明文化）
- runtime: flake を避けるため non-blocking から開始し、安定後に blocking 化

## Risks & mitigations
- analyzer由来ノイズ: CEM側 sanitize + 回帰テストで固定
- enum/型がCEMに載らない: 代表例の検証→分岐をPlanで先に確定
- strict validator の実装コスト: 対象を `viewer.html` から段階導入
- runtime flake: 対象最小化/リトライ/タイムアウト + non-blocking 開始
- MCP互換: text + structured の二重出力、段階導入

## Test strategy
- Unit: CEM sanitize/postprocess、diagnostics schema の整合
- Integration: `cem:analyze` 決定性、fast/strict validate の差分確認
- Runtime: viewer smoke + console error（最小セット）
